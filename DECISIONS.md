# Decisions

- Relay is plain Node `http` (no deps), single POST /relay endpoint, pass-through only — keeps it auditable in ~35 lines and avoids an Express dependency for a 20-line job.
- Relay verified first against real Moonshot endpoint with a deliberately invalid key: got back `invalid_authentication_error` from the actual API (not a CORS/network error), confirming pass-through works before any UI was built.
- No ES modules / bundler: all app files are plain scripts loaded via `<script src>` in dependency order onto `window`, so the app runs from `file://` without a static server (only the relay needs `node relay/server.js`).
- Single HTML shell (`index.html`) with tab-switched "screens" (Generate / Optimization / Judgment / Review Queue / Settings), all in one SPA, per the single-page-app constraint.
- App state (prompts, history, correction log, settings) lives in one global `AppState` object in `app.js`; export/import serializes it to JSON, always stripping the API key first.
- `props_used` is modeled as `{ ComponentName: { propName: value } }` (one prop-set per component name per generation) rather than per-instance — the schema in the spec doesn't disambiguate multiple instances of the same component, and this keeps validation tractable without inventing structure the spec didn't ask for.
- Live Generate-screen requests always score accuracy under `expected_behavior: "generate"` (never "refuse_or_substitute") — only hardcoded eval cases (section 6) carry a known ground-truth `expected_behavior`. A designer's free-form request has no such label, so a refusal there scores accuracy 0 by the same "false refusal is a failure" rule as everywhere else; documented here since it's the one place refusal-aware scoring can't be verified against a stated expectation.
- Judgment layer's one real rule ("error state must offer a next step") is approximated as `components_used.includes("Button") or includes("Alert")`, since the JSON schema has no `action` field on Alert to check directly — the schema in section 3 doesn't model button/alert actions as separate entities.
- Maker/Checker "training-set scores from the last evaluation" (section 7.1) is measured fresh at the start of every iteration (step 1 of 5), not read from a stale prior run — this doubles as the same-session baseline the Checker compares the candidate against (section 7.2's explicit requirement), so one measurement serves both purposes honestly.
- Prompt version `status` values: a version keeps `status: "live"` even after being superseded by a newer promotion — `AppState.prompts.liveId` is the single pointer for "current." `"rolled-back"` is reserved specifically for the version that gets displaced *by a rollback action* (as opposed to a normal forward promotion), so the five statuses in the spec each have a distinct, non-overlapping meaning.
- Rollback re-opens the same promotion-gate panel against the target version with no new Maker/Checker run (that version's numbers were already measured when it was first promoted) — satisfies "restores it through the same promotion gate" without re-litigating a decision already made.
- Held-out and Checker training runs both use `settings.runsPerCase` (default 3) rather than a hardcoded 3, since section 10 explicitly exposes runs-per-case as a setting and section 7 doesn't contradict that.
- Maker/Checker calls go through `ProviderAdapter.call` directly (not the per-request inner loop) since they're meta-level prompt authoring, not design-system-bound UI generation; the Maker gets one lightweight JSON-parse retry for robustness, mirroring the inner loop's philosophy without reusing its design-system-violation logic (which doesn't apply to prompt text).
- No ES module bundler was introduced, and no build step exists — `python -m http.server` or any static file server works for `index.html`; only LLM calls need `node relay/server.js` running alongside.

## Live verification notes (2026-08-03)

- The provided Moonshot key was rejected as `invalid_authentication_error` on **both** `api.moonshot.ai` and `api.moonshot.cn` — not the region-isolation case the spec warns about (that would 401 on exactly one region), just an invalid/inactive key. The adapter's region hint fired correctly on the international-endpoint 401 regardless.
- Re-verified everything against Groq's OpenAI-compatible endpoint (`https://api.groq.com/openai/v1`, `llama-3.3-70b-versatile`) instead — configured purely through Settings values, zero code changes, which is itself a live demonstration of the "changing provider must require only Settings, no code changes" requirement (section 1).
- Groq's free tier caps at 12,000 tokens/minute, which the training-set Checker batch (6 cases × full design-system-laden system prompt) gets close to on its own; the verification script needed short buffer delays between batches to avoid 429s. Not an app defect — the app's own error handling surfaced the 429 message verbatim, as required by section 11 ("never fake a result").

## Cloudflare deployment (2026-08-03)

- Deployed as a single Cloudflare Worker with static assets (`assets.directory: ./public`), not Workers + separate Pages — this is Cloudflare's current recommended pattern for a full-stack app (one deploy, one domain, no CORS between frontend and API route) and supersedes the older Pages + Pages Functions split.
- `worker/index.js` is the deployed equivalent of `relay/server.js`, with one deliberate difference: a `ALLOWED_HOSTS` allowlist (moonshot.ai, moonshot.cn, groq.com, openai.com). The local relay is a bare pass-through by design (spec section 1); once reachable from the public internet, an unrestricted pass-through of arbitrary `baseUrl`/headers/body is an open proxy / SSRF vector, so the deployed version closes that off. Add a host to the Set in `worker/index.js` to support another provider.
- `assets.run_worker_first: ["/relay"]` is required in `wrangler.jsonc` — without it, Cloudflare's local/edge asset router intercepts `/relay` before the Worker's `fetch()` handler ever runs (observed as a bare 405 on every POST to `/relay`, including from paths that don't exist), because the default asset-routing order only falls through to Worker code for paths with no matching behavior *and* the assets layer's own method handling takes precedence otherwise.
- `adapter.js`'s `RELAY_URL` is derived at runtime: relative `"/relay"` (same-origin, works with `wrangler dev` and the deployed Worker) unless the page is opened via `file://`, in which case it falls back to the standalone Node relay's absolute `http://localhost:8787/relay` — keeps both the original file://+node-relay workflow and the new wrangler-based workflow working without configuration.
- Bug caught during live verification: the Worker's first draft built the upstream URL with `new URL(path, baseUrl)`, which — because `path` starts with `/` — replaces `baseUrl`'s own path (`/openai/v1`) instead of appending to it. Groq's API returned a real, correctly-surfaced 404 (`Unknown request URL`) that made this obvious. Fixed to plain string concatenation (`${baseUrl}${path}`), matching what `relay/server.js` and `adapter.js` both already assumed.
- Live deployment: https://design-agent-eval-loop.bobinthomas.workers.dev — verified with a real Groq call end-to-end and a real 403 against a disallowed host.

## Bugs found via real usage (2026-08-03)

- `TokenRouter` (an OpenAI-compatible aggregator) requires provider-prefixed model ids (`moonshotai/kimi-k3-free`), not the bare Moonshot model name — added as a working example rather than baked into the adapter, since the adapter is provider-agnostic by design.
- `adapter.js#extractText` assumed `message.content` is always a string; some providers return `content: null` for certain completions. Crashed `.slice()` on the Settings test-connection status line. Fixed by coercing null to `""` in the adapter, plus a defensive fallback at the display site.
- Bigger issue: when the inner loop's parse/repair attempts are exhausted, the Generate screen's "Raw JSON" toggle was showing `JSON.stringify(item.result, null, 2)` — which is the literal string `"null"` when parsing failed, not the model's actual response. There was no way to see what the model actually returned when things went wrong, which directly violates section 11 ("never fake a result"). Fixed: the toggle now shows the last raw response text plus the parse error when `result` is null, and relabels itself "Raw response (unparsed)".
- Root cause of the parse failures themselves: completion token counts were landing exactly at each profile's `max_tokens` cap (900/900/300, on both the initial call and the repair call) — the signature of truncation, likely a reasoning-style model spending its budget before emitting the JSON answer. Raised `CONFORMIST`/`EXPLORER` to 1600 and `SPRINTER` to 700 (still meaningfully lower, preserving the "is a small call good enough" comparison the profile exists to test).

## UX follow-ups from real usage (2026-08-03)

- Added a per-card **Retry** button (shown on call failure, unparseable result, or a gate failure) that re-runs just that one profile against the same request — the automatic inner-loop repair (max 2 attempts, section 4) still only fires per-request; Retry is a separate, user-triggered fresh attempt, useful for transient errors like a Cloudflare 524 gateway timeout. A `AppState.retrying` Set drives a lightweight "Retrying…" card state; it's intentionally excluded from session export (transient UI state, not data) and reset on import.
- Replaced the plain labeled-block mockup with small per-component visual previews (`COMPONENT_PREVIEWS` in `app.js`), styled from each component's actual `props_used` (Button variant, Alert/Badge tone, Input state, etc.), plus the model's own `layout_description` shown as a caption underneath. This is still an approximation, not a true rendered composition — the JSON schema (section 3) is a flat `components_used` list with no parent/child relationship, so there's no hierarchy data to lay components out inside one another; documented as a visible limitation via the caption rather than pretending to compose a real nested layout.
- Settings (base URL, model, temperatures, runs-per-case) now persist to `localStorage` across refreshes — everything except the API key, which stays strictly memory-only per spec section 1 ("never write it into code, storage, or exports"). `loadPersistedSettings()` runs before the Settings form renders so saved values show up on load; the API key input is always blank on a fresh page load by design, called out directly in its label.
